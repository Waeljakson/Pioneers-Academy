# المعمارية والأمن

```text
Browser (React, Cairo, RTL)
       │ HTTPS + same-origin JSON + HttpOnly cookie
       ▼
Node.js / Express
  Origin check → session → role / ownership → Zod → transaction
       │ Drizzle + bound SQL parameters
       ▼
New independent Neon PostgreSQL
```

`DATABASE_URL` و`DATABASE_URL_DIRECT` تُقرأ في Node.js فقط. لا يوجد أي متغير VITE_ لقاعدة البيانات، ولا استيراد server/ في src/. لا يحوي build بيانات اعتماد. رابط الاتصال ليس API عامًا، ولا يصل المتصفح مباشرة إلى Postgres.

## الصلاحيات

| الدور | النطاق |
|---|---|
| admin | جميع الوحدات وإنشاء حسابات موظفين وتعطيل الحسابات |
| academic | إدارة البرامج والطلاب والمحاضرين والحضور والاختبارات والشهادات، دون المالية أو إدارة الموظفين |
| lecturer | محاضراته وطلاب دفعاته وسجل حضورها؛ إنشاء وتعديل الحضور الخاص بها فقط |
| finance | الفواتير والمدفوعات والمصروفات، وقراءة الطلاب للربط |
| student | بوابته الشخصية واختباراته وشهاداته فقط |

لا يكفي إخفاء الأزرار: يتحقق كل API محمي من الدور، وتتحقق مسارات الطالب من `user_id` الخاص بالجلسة. المحاضر لا يرسل هوية محاضر لاختيار نطاقه. منع قراءة `users` يستثني الإدارة فقط، وحتى المدير لا يتلقى password_hash.

## المصادقة

- Scrypt مع salt عشوائي مستقل لكل كلمة مرور، والمقارنة ثابتة الزمن.
- رمز جلسة عشوائي 256-bit؛ المخزن في قاعدة البيانات SHA-256 فقط.
- Cookie: HttpOnly + SameSite=Lax، وSecure في الإنتاج، صلاحية 8 ساعات.
- تغيير كلمة المرور وتعطيل الحساب يبطلان الجلسات. دور المستخدم وحالته يؤخذان من القاعدة في كل طلب.
- تحقق Origin مطابق تمامًا في كل طلب تغيير بما فيه login/logout، ونفس النطاق للواجهة وAPI؛ لا CORS مفتوح.
- عشر محاولات لكل بريد خلال 15 دقيقة عبر عداد ذري في قاعدة البيانات. للطرح العام واسع النطاق أضف rate limit على مستوى reverse proxy/WAF أيضًا؛ الحماية الحالية قد تسمح بمضايقة حساب معروف عبر استنفاد محاولاته.
- لا تتضمن رسائل الأخطاء تفاصيل SQL أو URL اتصال أو كلمة مرور.
- CSP وHelmet وCache-Control:no-store لاستجابات API، ولا localStorage للجلسات.

## سلامة البيانات

- UUID ومفاتيح أجنبية وقيود CHECK وUNIQUE. اسم الجدول وأسماء الأعمدة من قائمة خادم ثابتة، والقيم bound parameters بواسطة Drizzle.
- العلاقات بين البرنامج والمقرر والدفعة والتخصص تمنع الخلط بين البرامج.
- دفعة مالية تُنفذ داخل transaction مع قفل الفاتورة وحساب المدفوع قبل إدراج الجديد.
- محاولة اختبار واحدة لكل طالب/اختبار بقيد قاعدة البيانات، والتصحيح على الخادم. API الطالب لا يعيد correct_index.
- نشر الاختبار يتطلب وجود أسئلة. قفل صف الاختبار يمنع تزامن تعديل الأسئلة مع النشر أو التسليم.
- سجل audit للإنشاء والتعديل والتسليم، داخل المعاملة نفسها.
- الشهادة تتطلب تسجيلًا مكتملًا 100% وقت إصدارها، ومعرّف تحقق UUID عشوائي مستقل.

صفحة التحقق عامة لمن يعرف رابطها وتعرض اسم المتخرج والبرنامج والنوع والتاريخ وحالة الإلغاء فقط. لا تعرض البريد أو الهاتف أو الهوية أو المالية. أكواد التحقق غير متسلسلة. عند تغيير النطاق، يجب إعادة طباعة QR بالرابط الجديد.

## التشغيل والتوسعة

الـ API لا يعتمد على ذاكرة عملية الخادم لحفظ المستخدمين أو الجلسات؛ يمكن تشغيل أكثر من نسخة باستخدام القاعدة نفسها. جميع القوائم في MVP تُجلب كاملة، لذا أضف pagination والبحث من الخادم قبل أعداد كبيرة من الطلاب. أنشئ Neon branch مستقل للتطوير والاختبارات قبل ترحيلات الإنتاج، واستخدم حساب DB بصلاحيات تشغيل محدودة بعد الإعداد، ونسخًا احتياطية وخطة استعادة بحسب بيئة النشر.

ملفات migration هي SQL مُراجَعة يقرأها runner عبر Drizzle، وليست مخرجات drizzle-kit. parser الحالي يقسم عند `;` ومناسب للملف المرفق؛ عند إضافة دوال SQL أو triggers تحتوي فواصل منقوطة داخل bodies، طوّر runner أو انتقل إلى migrator يدعمها قبل التطبيق.
